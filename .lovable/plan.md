# Перенос сайта и RM OS на российский сервер с обновлением «по кнопке»

Да, так сделать можно. Схема: вы продолжаете работать в Lovable, код автоматически уезжает в GitHub, а на вашем российском сервере стоит «приёмник», который по нажатию кнопки забирает свежую версию и обновляет боевой сайт. Данные (объекты, заявки, чаты, фото) переезжают на этот же сервер, поэтому всё открывается из России без VPN.

## Как это будет выглядеть для вас

1. Вы правите что-то в Lovable и проверяете в превью.
2. Заходите в RM OS на своём домене → раздел «Обновление системы».
3. Видите: «Есть новая версия от 8 сентября, 14:20» и кнопку «Обновить».
4. Нажимаете — 2–4 минуты идёт полоса прогресса — сайт обновлён. Данные при этом не трогаются.
5. Если что-то пошло не так — кнопка «Вернуть предыдущую версию».

## Что переезжает на ваш сервер

- Сайт residence-more и RM OS (единое приложение, один домен).
- База данных: объекты, комплексы, клиенты, брони, заявки, чаты, подборки, статистика.
- Фотографии объектов и комплексов.
- Фиды ЦИАН и Яндекса, чтобы площадки скачивали их с российского адреса.
- Вход менеджеров (авторизация).

## Что нужно от вас

- Сервер: VPS в России (Timeweb / Selectel / Yandex Cloud). Ориентир: 4 CPU / 8 ГБ RAM / 80 ГБ SSD, ~1500–3000 ₽/мес. Я подскажу точную конфигурацию.
- Доступ к серверу (IP, логин, пароль или ключ).
- Домен уже есть — понадобится доступ к его DNS-записям.
- Подключить GitHub к проекту Lovable (кнопка в интерфейсе Lovable, делается за минуту).

## Этапы работ

### 1. Подготовка сервера
Ставим Docker, веб-сервер с автоматическим SSL, базу данных PostgreSQL и хранилище файлов. Всё в контейнерах — обновления не ломают систему.

### 2. Перенос данных
- Выгружаем текущую базу из Lovable Cloud и заливаем в базу на сервере — структура и содержимое сохраняются один в один.
- Скачиваем все фото из текущего хранилища и загружаем в файловое хранилище на сервере, пути в базе перенастраиваем.
- Заводим учётные записи менеджеров заново (пароли задаются при первом входе) — это единственное, что не переносится напрямую.
- После первого переноса добавляем команду повторной синхронизации, если понадобится догнать данные перед окончательным переключением.

### 3. Приложение на сервере
Собираем текущее приложение в образ и запускаем на сервере. Настройки (адреса базы, хранилища, ключи ЦИАН/Яндекса) хранятся в защищённом файле окружения на сервере, а не в коде.

### 4. Раздел «Обновление системы» в RM OS
Новая страница внутри RM OS, доступная только вам:
- показывает текущую установленную версию и последнюю доступную из Lovable;
- кнопка «Обновить» — сервер забирает новый код, собирает, применяет изменения структуры базы и переключает трафик без простоя;
- журнал обновлений: кто, когда, чем закончилось;
- кнопка отката на предыдущую версию;
- перед обновлением автоматически делается снимок базы.

### 5. Домен и запуск
Переводим DNS домена на IP сервера, выпускаем SSL, проверяем сайт, RM OS, отправку заявок, чат, фиды ЦИАН и Яндекса. Проверяем открытие с российского интернета без VPN.

### 6. Резервные копии и присмотр
Ежедневный бэкап базы и фото на отдельное хранилище, хранение 30 дней. Уведомление, если сайт упал.

## Важные ограничения (честно)

- **Две базы данных.** Превью в Lovable продолжит работать со своей тестовой базой, боевые данные будут только на вашем сервере. Реальные объекты и заявки заводятся на боевом домене, Lovable остаётся средой разработки. Это правильно и безопасно, но к этому надо привыкнуть.
- **ИИ-помощник.** Он работает через сервис Lovable AI, который из России может быть недоступен. Варианты: оставить как есть (может не работать), переключить на YandexGPT или GigaChat, либо ходить к нему через промежуточный зарубежный сервер. Решаем отдельно.
- **Ответственность за сервер.** Обновления системы, место на диске, продление домена — это уже ваша зона. Бэкапы и мониторинг настроим, но сервер живой и иногда требует внимания.
- **Правки структуры данных.** Если в Lovable я добавляю новое поле или таблицу, обновление по кнопке применит это на сервере автоматически. Но в редких случаях (переименование, сложные переделки) потребуется ручное сопровождение.
- **Сроки.** Первый запуск — ориентировочно 2–4 дня работы, из них ощутимая часть ждёт ваших доступов к серверу и домену.

## Техническая часть

- Хостинг: VPS в РФ, Docker Compose: `caddy` (reverse proxy + Let's Encrypt), `app` (TanStack Start в Node-режиме), `postgres:16`, `minio` (S3-совместимое хранилище фото), `watchtower`-подобный деплой-раннер.
- Приложение сейчас собрано под Cloudflare Workers — нужен перевод SSR-таргета на Node (`nitro`/node-server preset) и проверка серверных функций на совместимость.
- Backend: self-hosted Supabase (postgres + gotrue + postgrest + storage) вместо Lovable Cloud, чтобы `src/integrations/supabase/*` и все `.functions.ts` работали без переписывания. Переменные `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY` указывают на свой инстанс.
- Миграция данных: `pg_dump` из Lovable Cloud (роли/схемы `public` + `auth`), `pg_restore` в свой Postgres; фото — рекурсивная выгрузка бакета `property-photos` и заливка в MinIO с сохранением ключей.
- Обновление по кнопке: страница `/system/update` в RM OS → серверная функция дергает локальный deploy-агент (systemd unit со своим HTTP-эндпоинтом на 127.0.0.1, токен в env). Агент: `git pull` из GitHub-репозитория Lovable → `docker compose build` → `supabase db push` (миграции из `supabase/migrations`) → `docker compose up -d` с health-check → откат на предыдущий образ при неуспехе. Журнал в таблице `deployments`.
- Бэкапы: `pg_dump` + `mc mirror` по cron в объектное хранилище провайдера, retention 30 дней.
- Секреты (`CIAN_API_KEY`, `YANDEX_*`, `LOVABLE_CRON_SECRET`) переносятся в `.env` на сервере, cron ЦИАН перенастраивается на новый домен.
