# Синхронизация календаря с Яндекс Путешествиями и Суточно.ру

## Коротко про варианты

Без Бново — можно. Площадки отдают и принимают занятость по ссылкам iCal, этого достаточно, чтобы даты автоматически закрывались в обе стороны. Ограничение iCal одно: в нём приходят только даты и служебный номер брони — ФИО и телефон гостя площадки не передают. Это ограничение самих площадок, а не нашей реализации.

Бново нужен только если хочется видеть данные гостя и суммы. У Бново есть API, но доступ к нему выдаётся по заявке — как только доступ будет, подключим его отдельным этапом поверх той же схемы. Поэтому делаем так: сейчас — рабочая двусторонняя синхронизация по iCal, позже — обогащение данными из Бново.

## Этап 1. Импорт занятости с площадок

- Для каждого объекта в RM OS можно добавить несколько внешних календарей: название источника (Яндекс Путешествия, Суточно.ру, Бново, другое) и ссылка .ics.
- Раз в 30 минут система забирает эти ссылки, разбирает периоды и создаёт/обновляет брони в нашем календаре.
- Внешние брони выглядят в шахматке как обычные полосы, но помечены источником и другим цветом; редактировать даты вручную нельзя — они перезапишутся при следующей синхронизации. Комментарий и привязка клиента редактируются.
- Если брони на площадке больше нет — полоса автоматически исчезает.
- В карточке объекта показываем статус синхронизации: когда обновлялось, сколько броней, ошибка если ссылка недоступна.
- Кнопка «Синхронизировать сейчас».

## Этап 2. Экспорт нашей занятости на площадки

- Для каждого объекта генерируем постоянную ссылку вида `/api/public/ical/<токен>.ics`, которую вы вставляете в кабинет Яндекс Путешествий и Суточно.ру.
- В ленту попадают все не отменённые брони объекта, включая внешние из других источников — так площадки не пересекутся между собой.
- Ссылку можно скопировать одной кнопкой и при необходимости перевыпустить.

## Этап 3 (позже, по готовности доступа). Бново

Когда получите доступ к API Бново, добавляем подтягивание брони с ФИО, телефоном, суммой и источником — брони из iCal при этом дополняются реальными данными гостя вместо обезличенных.

## Технические детали

- Новые таблицы: `property_calendar_feeds` (объект, источник, url, токен, last_synced_at, last_error) и `property_ical_tokens` для экспорта; в `bookings` — поля `external_source`, `external_uid`, `external_feed_id`, уникальный индекс по `(external_feed_id, external_uid)`.
- Импорт — server function + публичный маршрут `src/routes/api/public/ical-sync.ts`, вызываемый по расписанию pg_cron с секретным заголовком. Парсер VEVENT пишем сами (без Node-only библиотек, ограничения Worker-рантайма).
- Экспорт — `src/routes/api/public/ical.$token.ts`, отдаёт text/calendar; токен случайный, PII в ленту не попадает.
- Проверка пересечений для ручных броней остаётся; внешние импортируются даже при конфликте, конфликт подсвечивается в календаре, чтобы не потерять данные молча.
- Даты трактуем по правилу iCal: DTEND — день выезда (эксклюзивно), в нашей модели `end_date` = DTEND минус один день.
