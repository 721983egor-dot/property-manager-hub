# Директ и Метрика в Ассистенте РМ ОС

Подготовлено 30.10.2026. До подключения токенов и обновления сервера интеграция не работает в production. Рабочие рекламные кампании этим кодом автоматически не изменяются.

## Возможности

Администратор: Настройки → Реклама (`/system/advertising`). Директ: параметры кампаний, расходы без НДС, показы/клики, результаты двух заявочных целей, отчёты по объявлениям и поисковым запросам. Метрика: UTM, визиты, посетители, отказы, глубина и длительность, достижения целей. Отдельное время обновления/ошибка/полнота у каждого источника; при ошибках прежний успешный снимок сохраняется. Отсутствие данных не превращается в нулевой расход.

CRM: точное сопоставление `utm_campaign`, `utm_source=yandex`, `utm_medium=cpc`; бюджет/CPL только в RUB. Сопоставление берётся из `UnifiedCampaign.TrackingParams`, для созданных вручную кампаний есть точные ID 715631828 → rm_rent_search и 715631494 → rm_owners_search. Если одну UTM используют несколько кампаний, заявки между ними не распределяются и CPL не вычисляется. Тестовые кампании `rm_analytics_test_*` исключены. Видны статусы заявок и текущие стадии связанных по lead_id сделок; это когорта заявок периода, не сделки, закрытые за период. Чаты не прибавляются к заявкам. Исторические обращения без меток не восстанавливаются.

Расходы за период / обращения, созданные за период — операционный CPL, не когортная окупаемость. Модели атрибуции: Директ AUTO, Метрика lastsign, CRM — последний сохранённый переход. Текущие сутки неполные, дата/время отчётов по Москве. Данные Яндекса обновляются с задержкой; отдельно передаются признаки семплирования и ограничения строк. Продажи/выручка/ROMI и передача офлайн-конверсий не реализованы.

До 10 000 сохранённых строк каждого отчёта; ограничение явно обозначается. UI показывает первые 100. Ассистент получает обзор до 100 строк, а остальные читает страницами через `getYandexAdvertisingDetails` (до 200 за вызов). Для полной аналитики нельзя считать отсутствующие в превью строки нулевыми.

## Инструменты Ассистента

- `getYandexMarketingConnection`: логин/счётчик/ID целей и факт наличия ключей, без значений ключей.
- `getYandexAdvertisingReport(days=1…90)`: сводка с CRM, метаданными свежести, ошибками и ограничениями источников.
- `getYandexAdvertisingDetails(days,source,offset,limit,campaignId?)`: следующая страница performance/ads/queries/metrika; campaignId применяется к данным Директа.
- `proposeYandexCampaignChange` → карточка → `applyYandexCampaignChange`: остановить/возобновить кампанию, добавить минус-фразы, изменить бюджет на существующий период и/или среднюю цену клика поддержанной поисковой ЕПК.

Правки лимитов поддержаны только для RUB ЕПК, Search=AVERAGE_CPC, Network=SERVING_OFF, BudgetType=CUSTOM_PERIOD_BUDGET, AutoContinue=NO. Сохраняются все прочитанные настройки стратегии, площадки и даты. Для других стратегий функция выдаёт понятную ошибку, не переключает их. Тексты объявлений, ключевые фразы, география и автоматическое создание кампаний пока не меняются этим инструментом.

Предложение сохраняется на сервере, связано с автором, конкретным подключением и хешем свежих параметров кампании, действует 30 минут. На подтверждении проверяются действующий администратор, автор, срок, подключение и свежая кампания. Клиент передаёт только случайный proposalId, а не произвольное тело API-запроса. Атомарная SQL-функция сериализует локальные изменения одной кампании и расходует предложение до сетевого вызова. Журнал пишется до обращения к Яндексу и после принятия. Повтор успешно выполненного proposalId возвращает прежний результат; executing/uncertain автоматически не повторяются. При сбое/таймауте проверить кабинет до нового подтверждения. После принятия выполняется чтение текущей кампании; статус модерации/состояние не объявляются активными показами автоматически. Изменения из кабинета между последней проверкой и API-вызовом невозможно исключить полностью — API не предоставляет нашего атомарного compare-and-swap.

## Подключение и выкладка

1. Коммит отправить в `preview`, обычным процессом выложить тест. Миграция `20261030150000_yandex_marketing.sql` создаёт server-only cache/actions и две RPC, закрытые для anon/authenticated. Preview и production используют общую БД; cron на preview пропускается. Новые таблицы не содержат токенов.
2. В аккаунте residence.more подготовлена форма приложения «РМ ОС — реклама и аналитика» (https://oauth.yandex.ru/client/new/api), права `metrika:read` и `direct:api`. Создание/выдача доступа пока НЕ подтверждены. Существующее `n8n disk` не изменялось. Яндекс может потребовать заявку на доступ к API Директа. Проверить это на странице приложения после создания.
3. После явного подтверждения владельцем выдать OAuth-доступ приложению. Токены вводить только в Настройки → Реклама, не в чат Ассистента, исходники или git. Один токен с обоими правами допустим в обоих полях. Они сохраняются сервером в существующем `platform_secrets`, доступном service_role; браузеру и модели значения не возвращаются. Пустое поле сохраняет прежнее значение. При смене кабинета нужны оба новых токена. Секреты приложения и токены не выводить в сообщения/логи.
4. Параметры: логин Директа residence-more, счётчик 97013300, tenantGoalId 676665001, ownerGoalId 676665229. При смене счётчика указать его собственные цели. Проверить UI и Ассистента как администратора; менеджер/аноним не должны читать настройки, отчёты или подтверждать предложения.
5. Нажать «Обновить статистику». Наличие сохранённого ключа не означает успешного подключения: проверить каждый источник. Отчёт Директа 201/202 означает «формируется», не пустую статистику. Повторные попытки ограничены; при ожидании повторить через несколько минут. Если очередь Директа не успела завершиться к границе часа, будет запрошен свежий отчёт.
6. Сравнить расходы за одинаковые даты без НДС с кабинетом Директа; цели отдельно с AUTO. Сопоставить UTM и заявки, исключить тесты. Проверить одно согласованное изменение на остановленной тестовой кампании: карточка, отказ от устаревшего подтверждения, повтор proposalId, аудит. Не тратить деньги ради теста и не возобновлять старую кампанию.
7. Рабочая публикация — по отдельной команде владельца согласно AGENTS.md. Контейнер stats-cron вызывает `/api/public/cron/yandex-marketing` каждые 10 минут; хранилище запускает успешное обновление не чаще раза в час для каждого источника/периода, а повтор ошибки — не чаще раза в 2 минуты. Автоматический фон поддерживает период 30 дней; остальные периоды обновляются при чтении. Кнопка UI может запросить внеочередное обновление с защитой от частых вызовов. После обновления пересоздать stats-cron обычным deploy-agent; API закрыт x-cron-secret.

Текущая среда не смогла получить/отправить origin (DNS github.com) и подключиться к rm-vps (Operation not permitted). Не считать локальную сборку публикацией и не утверждать, что реальные API-запросы/права уже проверены.

## Проверки

`node --import tsx --test src/lib/yandex-marketing/model.test.ts` — сохранение платформ/дат/лимитов стратегии, защита неподдержанных стратегий, добавление минус-фраз без затирания, границы суток Москвы, UTM по точному ID, сохранение больших ID объявления строкой, ограничение TSV, отложенный отчёт, отсутствие секретов в ошибках и метаданные семплирования Метрики.

`npm run build`, ESLint новых модулей, сравнение TypeScript с исходным HEAD. В репозитории есть прежние ошибки общего TypeScript; не объявлять весь проект прошедшим typecheck.
