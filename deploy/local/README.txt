Локальная тестовая РМ ОС

Адрес: http://127.0.0.1:4194/objects
Запуск: двойной щелчок по «Запустить локальную РМ ОС.command» в корне rm-os.
Либо: python3 scripts/local-dev.py start
Окно с запущенным приложением нужно оставить открытым.

Первый вход выполнен за пользователя admin@rm-os.test.
Случайный локальный пароль находится в LOCAL_ADMIN_PASSWORD файла
deploy/local/.env.local. Файл исключён из Git. Это отдельная тестовая учётная запись.

Установлено на этом Mac:
- Lima 2.2.1, бинарный архив проверен по SHA256SUMS официального релиза.
- Linux VM rm-os: 4 CPU, 4 ГБ памяти, диск до 30 ГБ.
- Состояние VM: ~/.rmos-lima (не удалять при обычной остановке).
- Инструменты Lima: соседняя папка local-rmos-runtime/tools.
- Docker в VM: отдельный проект rmos-local и постоянные local_db/local_storage volumes.
- Host-приложение Vite: 127.0.0.1:4194; локальный API: 127.0.0.1:54321.
- Папка исходников доступна VM только для чтения.

Команды из корня rm-os:
python3 scripts/local-dev.py status   — состояние служб
python3 scripts/local-dev.py setup    — запустить службы и дождаться готовности
python3 scripts/local-dev.py migrate  — применить ещё не применённые миграции к тестовой базе
python3 scripts/local-dev.py seed     — добавить вымышленные примеры один раз
python3 scripts/local-dev.py dev      — запустить интерфейс после старта служб
python3 scripts/local-dev.py logs     — последние сообщения служб
python3 scripts/local-dev.py stop     — остановить службы, сохранив тестовые данные
После работы интерфейс останавливается Ctrl+C в окне запуска.

Изоляция:
Существующая .env рабочего проекта не менялась. Для локального приложения
адрес базы, ключи и проект явно переопределены. Реальные API-ключи, бот,
площадочные интеграции и агент публикации не подключены; фоновые cron-службы
и Telegram poller не запускаются. Метрика/маркетинговый трекинг отключены
в режиме localtest. Все демонстрационные объекты отмечены [ТЕСТ].
Серия «Ежемесячный сервер» — только вымышленный пример, не запись реального расхода.
Поручение о реальном расходе VDSina хранится отдельно в recovery-pending.

Разработка и восстановление:
Изменения кода сохранять в Git preview. Не выгружать локальную тестовую базу
поверх восстановленной базы Beget. Полученные бэкапы сначала восстановить
в отдельную базу на российском сервере, проверить дату, целостность,
фото/документы и исходные ключи расшифровки. Затем применить новые миграции
и проверить обновлённое приложение на восстановленных данных.
Демонстрационные данные в рабочую систему не переносить.

Ограничения:
Фото настоящих объектов и текущих клиентов в тестовой базе нет.
Ассистент и внешние площадки потребуют отдельной настройки тестовых ключей.
Закрытые договоры с шифрованием пока требуют отдельного локального LEASE_DATA_KEY;
старый ключ восстановления нельзя заменять новым при переносе реальных договоров.
